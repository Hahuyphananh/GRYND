## [Unreleased] — Pre-launch hardening

### Added
- **Monetag ads, on the same terms as AdSense** — the second ad provider is wired in without loosening a single rule of the existing ad model: one loader (`src/components/MonetagScript.tsx`) rendered per page on **exactly the pages that already render the AdSense loader** (the four main pages plus each game lobby whose board lives on its own match route), never in the root layout, never on a match route, and never on the games whose lobby and board are one page — so no popunder, vignette or in-page-push unit can interrupt a match in progress. It is **entitlement-gated server-side** through the same `getMembershipTier` check as every other GRYND PRO perk (`isAdFreeViewer`, memoized per request), so a member's response contains no Monetag tag at all, and the zone id is configuration (`NEXT_PUBLIC_MONETAG_ZONE`, `NEXT_PUBLIC_MONETAG_ENABLED=false` to switch the provider off) rather than a literal in a component: a malformed zone emits nothing instead of loading a zone that isn't ours. The CSP gained the four host families the zone's own config uses (`quge5.com`, `auqot.com`, `ekhay.com`, `b3mny.com`) in `frame-src` — `script-src`/`img-src`/`connect-src` already allowed all of `https:`, so without the frame hosts the loader would download and then silently paint nothing. Unlike the AdSense tag this one is not a certified CMP and delivers no consent prompt, so it loads with the page for every non-member; the consent-gated third parties (GA4, PostHog, Sentry) keep their own gating untouched. The network's worker file is served from **public/sw1.js** for zone `12031484` — served, never registered: it is the same file the dashboard hands out as `sw.js`, renamed by hand so it cannot overwrite next-pwa's, and **not requested by anything today**, because the file's name is decided by the zone itself (its endpoint answers `"swName":"sw.js"`, and next-pwa owns that path). It is served with `Cache-Control: no-store` and an explicit `Service-Worker-Allowed: /` (next.config.js) so it is ready the day Monetag renames it: a cached worker file can pin an update to a stale revision, and a worker's scope is its own directory. Registering it from our own code is what would break things — a second worker at the root scope displaces next-pwa's — and Monetag's worker installs a `fetch` handler (verified by executing it), so folding it into next-pwa's worker is a deliberate change, not a tidy-up. Note the copy of that file that used to sit at the REPO ROOT was never reachable — only `public/` is served — which is the same trap the older root `sw.js` is still in. Verified against a real production build (`next start`): `/`, `/classement`, `/profil` and every `/games/<slug>/play` lobby emit `<script id="monetag-multitag" async data-cfasync="false" data-zone="295730" src="https://quge5.com/88/tag.min.js">`, while `/games/odds/play`, every match route, `/stats`, `/rooms/join` and `/upgrade-pro` emit neither provider's tag. Verify with `npm run test:ads`.
- **Private custom rooms (GRYND PRO) & free friend challenges** — invite-only matches for the three games whose own store can seat a NAMED pair (Pool Masters, Precision, Tower Arena), built on the existing lobby/invitation/auth/realtime systems and changing nothing about public matchmaking. A room is its own record (migration `0217`: `private_rooms` + `private_room_members`, persistent, additive, no existing table touched) that carries who may be in it, the game, validated settings, and — once started — which real match it became; **the match itself is always created by the game's own store** through a primitive reused from that game (`createPoolMatchForPair`, `createPrecisionMatchForPair`, `createTowerArenaMatchForPair`), so no game state is re-implemented. **Only an active PRO member can CREATE a room**, checked server-side per request through the existing `getMembershipTier` (never a body field, never a hidden button), while **joining a room you were invited to, and challenging a friend, stay free** — a challenge is structurally not a room (no code, one invitee, server-chosen free settings, and it starts when the friend accepts), which is what keeps it free without handing every account standalone room-creation privileges. Room codes are 10 characters from a 32-symbol unambiguous alphabet with a unique index, joined through a rate-limited endpoint, and a room's details are readable only by its participants. Concurrency is handled where it is decided: joins lock the room row (`FOR UPDATE`) and count seats inside that transaction, a start or a challenge acceptance claims the room with a single conditional `UPDATE … WHERE status='open' RETURNING` so exactly one caller can mint a match, a failed creation releases the room instead of leaving a ghost, and a claim abandoned mid-create is released by the lazy sweep (no cron needed for correctness). **Friend challenges are now a button on each friend in the existing Friends tab** (pick game → send → the friend accepts or declines → both land in the match), the invited player is notified on the existing realtime transport through a new SERVER-VERIFIED per-user room (`user:join` derives the id from the Clerk subject; the generic `join_room` refuses that prefix, and the signal carries no room, code or game — only "refetch"), with a 20s visible-tab poll as the backstop. Adds `/rooms/[roomId]` and `/rooms/join?code=` pages and a rooms panel in the profile's Friends tab, all translated in en/fr/es with loading, empty and error states. Requires `npm run db:migrate` (migration `0217`; the tables and the duplicate-guard index are created with `IF NOT EXISTS`). Verify with `npm run test:rooms` (58 assertions: PRO-vs-free creation, IDOR, expiry, duplicates, full rooms, replayed answers, stake caps, and the concurrency/source contracts).
- **Active players per game (backend)** — a per-game active-player presence foundation for a future "N playing" lobby badge: the dormant `user_game_presence` table is adopted and extended (migration `0159`), heartbeats land through `POST /api/presence/active-game` (idempotent upsert on `(user_id, game_key)`, 60s cadence, 3-minute activity window, so closed tabs age out on their own), and `GET /api/casino/active-players` returns Redis-cached aggregate counts only. No user data is ever returned. The games now report into it (next bullet); only the lobby badge itself is still to come.
- **Active players per game (game wiring)** — every casino game reports presence from the lifecycle signal it already had, through one shared hook (`useActiveGamePresence`): `<CreatorModeHost>` beats while `autoStart && !autoStop` and clears the moment `autoStop` fires (21 mounts), and the four pages that mount no host (Crash Arena tables, Pool Masters, Hex Duel, Odds) call the same hook next to their existing "a real session started" edge. Players still in a matchmaking takeover are not counted, spectators on a shared live match never are (`presenceEnabled`), a finished match clears immediately, and two tabs of one game still count once. Presence is best-effort — every request failure is swallowed, so a presence outage cannot touch gameplay, wagering, XP or matchmaking. Verify with `npm run test:presence` and `npm run verify:game-presence`.
- **Active players per game (lobby UI)** — every casino game card now shows how many players are inside that game right now (`● 12 playing`, `🔥 127 playing` for a busy game, `No players right now` when nobody is in it) in the footer of the existing `GameCard`, so the All Games grid and the For You strip share one card and one badge. One 20s poll of `GET /api/casino/active-players` covers the whole lobby, pauses while the tab is hidden, and cleans up on unmount; counts are mapped with the card's own game id and are never hardcoded. A failed read hides the badge rather than showing a misleading zero, and filters, sorting, search, links and recommendations are unaffected. The label is real text (never colour alone), lives outside the card's link so screen readers read it, and is localized in en / fr / es. Verify with `npm run verify:lobby-for-you` (six viewports, plus a control page with the badge removed).

The welcome tutorial gained one warm follow-up line derived from the answers. Requires `npm run db:migrate` (migrations `0157`, `0158`).

- **Barricade (free practice)** — the 9×9 barricade race is playable against a local bot at `/casino/barricade/play-ai`: a responsive board that renders the rules engine's own state (pawns, placed barricades, remaining counters, turn badge, highlighted legal destinations, goal baselines), a barricade mode with horizontal/vertical orientation and an engine-verified preview that says why a groove is refused, win/defeat through the shared result screen, Restart and back-to-lobby. Easy/Normal/Hard bots decide through the same `legalActions`/`applyAction` the player uses and are bounded by both a node budget and a 250 ms clock, so no search can freeze the tab. Free play only — no wager, no second human, no server-side match and no rating or trophy progress — and the route is registered in `GAME_ROUTE_PATTERNS` so a signed-out visitor can read it. - **Barricade (online 1v1)** — the 9×9 barricade race is now playable against a real opponent at `/games/barricade/play` (lobby) and `/games/barricade/<matchId>` (match), with direct match creation and joining (`create-or-join` fills the oldest open lobby or opens a new one), a waiting room the creator can cancel, live board and turn synchronisation over the existing Socket.IO per-match room, both players' remaining barricades, resignation, disconnect forfeits with reconnection, and the shared result screen for victory/defeat. **The server owns everything**: the only gameplay request is an action ADDRESS plus `expectedVersion`, and the position, both reserves, the turn, legality, the winner and the result are all derived by the shared rules engine inside a row-locked transaction, so a stale tab, a double submit or a replayed turn is refused (the `barricade_moves` unique `(match_id, ply)` index makes one action per turn a storage invariant). Online play requires an age-verified account — signed-out visitors keep the free browser-only practice board — and Barricade stays unstaked. The catalogue, rating and quick-queue registration landed with the platform-integration entry below. Dice Flush is untouched. Requires `npm run db:migrate` (migration `0207`). - **Performance statistics dashboard (GRYND PRO)** — `/stats` is a per-player analytics surface with NO new source of truth: every figure is read from the journals the settlement writers already maintain (`rating_events`, `trophy_events`) plus the per-game `player_ratings` / `player_trophies` rows, so nothing is recorded twice and no game's match table is scanned. It reports total settled matches with wins/losses/draws, an overall win rate that EXCLUDES draws from the denominator (the platform's own rule — `applyLeaderboardCounters` has no draw branch) and reads `—` rather than 0% when nothing is decided, a per-game breakdown (record, win rate, current Elo, current trophies), Elo / trophy / Overall Elo curves and recent results, filterable by game and date range and paginated in SQL. A match is counted ONCE across the union of both journals (the multi-seat tables settle trophies only), and games with no reliable result (Hex Duel — unrated; every solo/AI mode) appear nowhere rather than as a fabricated 0% win rate. Charts are hand-rolled SVG (no charting dependency was added — the repository has none), labelled per metric with dated axes, tooltips and keyboard-reachable points, and each has honest loading, empty and error states.
- **Historical ranking progression (GRYND PRO)** — the platform's established cross-game metric is **Overall Elo** (the mean of a player's established per-game ratings, the same rule `fetchOverallEloLeaderboard` orders by), and its history now exists: migration `0216` adds `player_rank_snapshots` (one row per player per UTC day, unique on `(user_id, bucket)`, indexed for the player+date read and the per-day sweep, persistent, never back-filled), `GET /api/jobs/rank-snapshots` records every ranked player's position once a day (single idempotent `INSERT … ON CONFLICT (user_id, bucket) DO UPDATE`, wired to Vercel Cron at 21:00), and opening the dashboard refreshes the requesting player's own day the same idempotent way. Ranks are computed exactly as the board orders them, so a stored rank cannot disagree with the leaderboard; a player who is not ranked yet produces no row and the UI says the curve has not started instead of inventing a line from today's rank. The dashboard's per-game Elo curve is rebuilt from the recorded matches (its last point equals the value the profile shows today) — no history is ever synthesised. Requires `npm run db:migrate` (migration `0216`).
- **Pro analytics are gated on the server** — `/api/stats/performance` requires a session (401 otherwise), resolves membership per request through the existing authoritative check (`getMembershipTier`, the same one `/api/membership/status` uses — never a client-supplied `isPro`/premium flag, and there is no such parameter anywhere), is rate limited and `private, no-store`, and a non-member receives `{ pro: false, locked: true }` with NO analytics at all — not the totals, not the series, not the recent results — while the page renders an upgrade prompt from that shape. Everything free is untouched: the profile statistics, rank, leaderboards and ordinary match history keep their own endpoints, `/stats` is `noindex` and reachable only through the profile's new link. - **GRYND PRO pricing → CAD, presented in the visitor's own currency** — the membership catalog is now priced in Canadian dollars (`CA$3.49/week`, `CA$9.99/month`, `CA$59.99/year` — the approved amounts are unchanged; only the currency they are expressed in moved), and the upgrade surface shows a visitor the price in the currency their country resolves to: CAD, USD, EUR, GBP or AUD (`src/lib/currency.ts` — eurozone countries → EUR, GB → GBP, US → USD, AU → AUD, everything else → CAD, which is deliberate: a European country that does not use the euro, Poland for instance, must not be shown EUR). The country is read from the request's geo headers on the server (`/api/membership/status`, `src/app/upgrade-pro/page.tsx`), never from the client, so a visitor cannot shop a cheaper currency. **Nothing converts money in code**: a localized amount is read from the bound Stripe Price's own `currency_options`, and only when EVERY one of the three options carries an amount for that currency — a partial configuration falls back to CAD for all three, because the advertised savings compare the options against each other and a mixed set would be comparing two currencies. Checkout charges what the page showed: `/api/stripe/subscribe` passes a currency only after `resolvePriceCharge` has confirmed the bound price carries it, and records the currency it charged. That is why the per-currency amounts must be added to the GRYND PRO prices in the Stripe Dashboard (Stripe offers the conversion there) for USD/EUR/GBP/AUD; until then every visitor sees CAD, which is exactly what they are charged. Existing USD subscribers keep their current price — a subscription's currency is fixed, and changing billing interval now answers with an actionable message instead of an opaque Stripe error when the target price is not priced in the subscription's currency. Verify with `npm run test:multicurrency` and `npm run test:upgrade-pro`. The retired token-package prices remain in USD and are untouched (the Shop is gone).

- **GRYND PRO offer now advertises only the benefits the membership really grants** — the perk list existed four times over (the upgrade page's fixed keys, the fallback perk constants, the plan row the API serves, and the Stripe product description) and every copy had drifted to the same six lines, three of which were not true: profile customization (which GRYND does not sell as an exclusive perk), priority support (no such service exists) and detailed match history (no such feature exists). All four surfaces now derive from ONE approved catalog, `src/lib/proBenefits.ts`, and a benefit may only be ADVERTISED while the entitlement behind it is enforced server-side — so the offer currently lists exactly two lines, **ad-free browsing and gaming** (`src/lib/adEntitlement.ts` skips the AdSense loader and every ad unit for a verified member in the server-rendered response) and **priority matchmaking** (a bounded queue tie-break between already-compatible players in `src/lib/quickQueueWorker.ts` + `quickQueue.ts` — it never widens the skill window, never overrides a game/mode/region constraint and can never starve a free player). The approved-but-unbuilt benefits — advanced statistics and performance analytics with graphs, extended leaderboard access with ranking-progression graphs, and private custom rooms — are recorded in the catalog and translated in en/fr/es, but they are marked `planned` and are deliberately NOT rendered on the upgrade page, the modal, the PRO widget, the Stripe product description or the plan row: the change that implements each one flips its availability and adds it to the enforcement map the test suite checks. `tests/pro-benefits.test.mjs` fails if an advertised benefit has no enforcement site, if a planned benefit reaches a perk list, if the migration's perk row drifts from the catalog, or if a retracted claim reappears; `tests/upgrade-pro-contract.test.mjs` was updated to assert the catalog wiring instead of the old fixed key list. The Stripe product description is reconciled to the new copy on the next `ensureSubscriptionPlanStripe` call (a description is part of no price, so nothing about an existing subscription changes), and migration `0215` corrects the `token_subscription_plans` perk row that `/api/membership/status` serves — `npm run db:migrate` applies only that UPDATE; no price, product binding, subscription, interval or amount is touched, and all three billing options keep their existing savings calculations.
- **Profile customization is now free for everyone** — the custom chat name colour and the profile accent colour were both GRYND PRO perks. They are not part of the membership offer any more, so the membership check is gone from `POST /api/user/chat-color` and `POST /api/user/profile-customization` (both stay auth-required and still write only the caller's own row, with the same strict `#RRGGBB` validation), the profile screen shows the pickers to every signed-in player and no longer prints "GRYND PRO perk", "Unlock custom chat colors with a GRYND PRO membership" or the GRYND PRO badge on those cards, and the colour is no longer hidden from non-members where it is rendered — the chat feed and the live socket message, the Dice Flush room state, the Precision seat badges and the client-side (vs-AI) seats all used to null it out for a free account, which would have made the picker save a value nobody ever sees; the token-subscription join that existed only to compute that flag is gone with it (one less join per request). Existing members keep whatever they saved. Chat colour still loses to an equipped catalog glow, and **friend challenges stay free** — inviting a friend, accepting an invitation and joining an invited match were never gated and still are not; only private-room creation remains a Pro benefit (to be implemented).

### Fixed
- **Find a Match dropped a lone player onto an empty board** — clicking Find a Match with nobody else queued opened a lobby and then navigated straight to `/casino/barrier-blitz/<matchId>`, i.e. to the game page with no opponent and a "waiting" banner. The route answers in two situations that must not look the same: `joined: true` means the caller took an OPEN seat (the match is already live, so navigating is correct), while `joined: false` means they now OWN a fresh WAITING lobby — and in that case the lobby now stays exactly where it is and shows the shared matchmaking takeover (the same `MatchWaiting` screen every other game uses, with the player's own seat and a Cancel table action), navigating only when the server reports the match `playing`. The wait ends on the server's own status (the match read the match view polls, plus the lobby socket push as the fast path and a 2.5s visible-tab poll as the backstop), never on a client guess or a timer, and resuming an owned lobby from the open-tables list re-enters that same waiting screen instead of the board. Cancelling closes the lobby and ends the wait. Verified in a real browser against the shipping components with a scripted backend — nobody joining, an opponent joining, and cancel — via `npm run verify:barrier-blitz-matchmaking`.
- **What Monetag's one tag actually installs (verified, not assumed)** — the zone this property runs (`295730`) is a MultiTag, so the one tag already in the browsing pages is what activates **all four** formats, Onclick included: Monetag's own documentation states the tag carries four formats, the tag's own `function onclick` code is the Onclick implementation, and its zone answer pulls the other three scripts (Vignette `z=12031483`, and the two others via `z=12031484` / `z=12031482` — which of those two the dashboard calls Push Notifications vs In-Page Push is not announced by the files, so name them by zone id). All absolute-URL builders (OG/Twitter images, canonical + JSON-LD ids, the sitemap, email links) now resolve the origin through `src/lib/siteUrl.ts`, which ignores a retired, malformed or empty configured host and falls back to the live domain, so a stale build-time env var can no longer emit dead URLs. Still set `NEXT_PUBLIC_BASE_URL=https://www.grynd.dedyn.io` on the host and redeploy (the value is inlined at build time), then re-scrape the URL in each platform's debugger to clear its cached card.
- **Active players per game (QA pass)** — a Tower Arena player eliminated mid-match stays on the live page watching the survivors, and was being counted as "playing" for as long as they stayed; presence now opts out at elimination (Creator Mode still records the whole match), which brings it in line with the spectator rule on chess, four-in-a-row, poker, dots-and-boxes and hex-duel. The unmount clear is now gated on "this mount actually beat" rather than on the current opt-in flag, so a player who stops counting this way still clears their row the moment they leave. And the daily retention sweep no longer reimplements the presence DELETE as raw SQL — it calls the store's `pruneStalePresence()`, leaving one implementation in the module that owns the table.
